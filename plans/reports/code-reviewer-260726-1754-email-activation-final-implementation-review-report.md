## New Critical/High findings

### High — V11 backfill has zero automated regression coverage
Phase-04 step "1b" explicitly requires an assertion that a pre-existing `password_hash NOT NULL` row ends up `email_verified=true` after V11, and that an SSO row is untouched. Grepped `src/test` for `V11`, `backfill`, `password_hash IS NOT NULL` — no hits outside doc comments in unrelated files. No test seeds a row *before* V11 runs (all current integration tests boot against a fresh schema where V11 already ran, so a pre-existing account never exists to backfill). This is the exact mechanism preventing the red-team's Critical Finding #1 (mass lockout of the whole existing user base) — reading the SQL confirms it's correct today, but there is no CI trip-wire if a future migration edit (e.g. someone "cleans up" V11, or a V12 touches `email_verified`) silently reintroduces the lockout. Recommend a dedicated Flyway-callback test or a raw-JDBC insert-before-migrate test, per the plan's own risk note.

### High — Kill-switch rollback path is broken on the frontend
Verified by reading `AuthController.register` (disabled branch returns `UserInfoResponse` + `Set-Cookie`, i.e. a live session) against `AuthService.register()` and `RegisterPageComponent.submit()`: the FE unconditionally routes every `register()` response through the "check your inbox" confirmation screen and never calls `_user.set()`. Grepped `engly-fe/src` for `EMAIL_VERIFICATION_ENABLED`/`killSwitch` — **zero references**. So when ops sets `EMAIL_VERIFICATION_ENABLED=false` (the documented emergency rollback — "no redeploy needed"), the backend *does* issue a real session (cookies are set), but the SPA shows the user a "we emailed you a link" screen instead of logging them in, contradicting the plan's stated intent ("today's behavior") and the deployment-guide's promise of an instant, transparent revert. The user is technically authenticated (cookie exists) but the UI doesn't reflect it until a manual page reload triggers `ensureLoaded()`. No test (backend or frontend) exercises this combination end-to-end through the SPA. This only matters during an actual incident (SMTP down, ops flips the switch) — exactly when a confusing UI is worst.

## Medium findings

### Medium — "SMTP failure is non-fatal" acceptance criterion not actually tested
Phase-04 step 2 requires: "Register succeeds (202, token row created) even when the mocked sender throws — proves SMTP failure is non-fatal." `AuthActivationFlowTest.register_always_createsToken()` does not stub `doThrow` on the mocked `ActivationEmailSender` — it only re-asserts normal-path persistence (duplicate of `register_returns202_noSetCookie_bodyHasEmail`). Evidence of an abandoned attempt: `import static org.mockito.Mockito.doThrow;` is present in the file but **never referenced**. The real source is correct by inspection (`ActivationEmailSender.send()` try/catches everything), but note: the dispatch happens inside a `TransactionSynchronizationManager.afterCommit()` callback, and Spring's `TransactionSynchronizationUtils.invokeAfterCommit()` does **not** swallow exceptions thrown by synchronization callbacks — if a future change to `ActivationEmailSender` ever let an exception past its own try/catch, it would propagate out of `startVerification()`'s enclosing commit and surface as a 500 to the register/resend caller, silently breaking the "never fails registration" guarantee. There is no regression test protecting this seam. Recommend either implementing the originally-planned mocked-throw test (stubbing the mock to itself swallow, mirroring the real component) or adding a direct unit test on `ActivationEmailSender` asserting `mailSender.send()` throwing does not propagate.

### Low
- `EmailVerificationServiceTest.startVerification_tokenPersistsRegardlessOfEmailSendStatus` is a near-duplicate of `startVerification_persistsHashedToken_andDispatchesViaEmailSender` (same assertions, same non-throwing mock) — its own comment says the real failure-mode test lives in `AuthActivationFlowTest`, but that test (see Medium above) doesn't actually cover it either. Net effect: the "SMTP failure is non-fatal" claim is asserted nowhere at the test level, only true by code reading.
- No unit test directly targets `ActivationEmailSender` in isolation (e.g. injecting a `JavaMailSender` mock that throws `MailSendException` and asserting no propagation). Its correctness is currently only confirmed by manual source reading in this review, not by CI.
- k8s `20-engly-be-backend.yaml` bakes `MAIL_HOST=localhost` / `MAIL_PORT=1025` / auth+TLS both `false` directly into the deployment (not just `.env.example`). Read the whole file: this is consistent with every other var in it (DB_URL → local `postgres` Service, S3 → local Floci emulator, `AWS_ACCESS_KEY_ID=test`, `FRONTEND_URL=http://localhost:4200`) — the file is explicitly the **local OrbStack dev manifest** (header comment: "Image is built locally into OrbStack's shared store"), not a prod overlay. Not a defect, just noting it for anyone tempted to copy this file straight into a prod cluster without swapping every one of these dev defaults, mail included.
